# 便携式多目标 Rust 工具链改进计划

日期：2026-09-27

分析基线：仓库提交 `18720fc`（`fix to 1.98`）及当前工作树。
实施约束：**现有对外接口完全不变**。本次仅形成分析和计划，不实施工具链、安装器或发布流程改动。

## 1. 结论与适用范围

本项目已经具备完整的产品骨架：在 Windows 上部署目录内自包含的 Rust/Zig 工具链，构建两个 Linux musl 目标、一个 Cortex-M 裸机目标及 Windows 主机程序，并通过离线安装器交付。近期补齐的 Windows 链接输入、运行时 shim、目标标准库实体检查和提交门禁，都应当保留并继续完善。

下一阶段的重点应当是让“便携、自包含、离线、可重复交付”成为从首次安装到最终客户使用都可以验证的性质。最重要的投入顺序是：

1. 固定兼容性基线，补齐首次安装和路径搬迁能力。
2. 验证真正被交付的载荷，闭合下载、复制、安装、分片发布各阶段的完整性链路。
3. 消除并发构建、全局环境、配置修复和中途失败造成的状态污染。
4. 扩充真实依赖、宿主工具混入和目标运行行为的验证。
5. 在上述保证成立后，优化维护成本、包体积和构建耗时。

不建议把本轮工作变成新增目标、切换 Windows ABI、追逐新编译器版本或重做 CLI。Rust 固定为当前的 `1.98.0`，Zig 固定为当前的 `0.13.0`；版本升级应另立兼容性评估，不混入本计划。

## 2. 当前功能与架构

### 2.1 目标与构建能力

| 目标 | 实际角色 | 当前实现 | 交付边界 |
|---|---|---|---|
| `x86_64-pc-windows-msvc` | Windows 主机程序；其他目标的 build script、proc-macro 宿主 | 固定 Rust 主机工具链 + `rust-lld` + 本地 Windows 导入库和 `rpc_winshim.lib` | 保持 MSVC Rust ABI；不要求客户安装 VS/SDK 才能完成已覆盖的链接 |
| `armv7-unknown-linux-musleabihf` | ARMv7 Linux、musl、硬浮点 | Rust std + Zig C/linker wrapper | 默认 release，产物位于项目的对应 target 目录 |
| `aarch64-unknown-linux-musl` | ARM64 Linux、musl | Rust std + Zig C/linker wrapper | wrapper 目前过滤 Cortex-A53 erratum 链接选项，需要专项审查 |
| `thumbv7em-none-eabihf` | Cortex-M4F/M7 裸机 | core/alloc/compiler_builtins + `rust-lld` + 项目链接脚本 | 不要求 libstd；固件样例提供 ELF 到 BIN/HEX 的转换 |

Windows 原生构建中的 C 编译器实际使用 `zig cc -target x86_64-windows-gnu`，其对象参与最终 MSVC 目标链接。这不等于整个 Windows 工具链切换为 GNU ABI，也不能推导为支持任意 C++ ABI 混用。需要微软专有头文件的依赖、尚未覆盖的 CRT 符号，仍有明确边界。

### 2.3 当前交付链路及关键断点

```text
在线准备 tools/
    -> 源目录目标载荷检查/必要时修复
    -> 在源目录生成 Windows sysroot
    -> 在源目录运行 Windows 自包含检查
    -> 复制 core 与目标文件到 dist/staging
    -> 写 install-layout.json
    -> Inno Setup 编译 EXE
    -> 导出 EXE、发布分片及清单
    -> 客户安装、finalize、尽力执行安装校验
```

当前主要断点是：源目录通过验证不代表复制后的 staging、最终 EXE 或客户安装结果也通过验证；外层安装包有哈希不代表内部所有组件都与受管编译器对应；编译成功不代表交叉目标运行行为、所有 C 依赖和路径搬迁均正确。

### 3.2 兼容性判定规则

- **外部调用零迁移**：原有命令、项目布局和 HEC 探测方式继续工作。
- **合法输入的既有语义保持**：日志中已使用的输出路径、成功标记和错误分类先纳入基线；详细新增诊断优先写内部报告，不随意更改现有输出流结构。
- **数据契约不借机扩展**：新摘要、发布证明、耗时等存入内部报告或私有校验文件，不要求任何现有 JSON 消费者理解新字段。生成时间和内容哈希随构建变化属于正常数据变化，不属于 schema 变化。
- **缺陷修复需明确边界**：校验失败的文件、越界清单、缺失产物不属于合法成功输入；更早阻止此类损坏进入发布可以实施。若拟改变合法调用的默认行为，则移出本轮。
- **不暗改几个敏感行为**：不把 `-Validate` 当前的警告式健康检查直接改成强制非零退出；不把默认 CI 的 SKIP 政策改成全部硬失败；不自动给客户构建加全局 `--offline`/`--locked`；不把安装器恢复成目标勾选页面。
- **已有副作用也要核对**：构建后环境是否仍激活、已有 Cargo 配置的修复范围、安装时 PATH 写入，都要先记录。只修复可证明违背既有承诺的污染；无法证明等价的行为变更不作为“内部重构”混入。

## 4. 重要改进点总览

P0 表示可能交付不可用载荷、破坏便携性或造成跨目录误操作，应优先进入实施；P1 表示扩展可靠使用范围及避免重复故障；P2 表示在正确性稳定后优化成本。

| 编号 | 优先级 | 问题及证据强度 | 主要影响 |
|---|---|---|---|
| U01 | P0，前置 | 对外契约散落在脚本、JSON、文档和 OpenSpec；多个事实已发生漂移，源码确认 | 内部修复误伤 HEC、安装及脚本调用 |
| U02 | P0 | setup 未调用 Windows 链接输入生成器，而所有构建入口都检查该输入，源码确认 | 全新源码安装后，首次构建仍缺必需输入 |
| U03 | P0 | Windows `/LIBPATH` 以空格串拼接；native wrapper 以 ASCII 嵌入绝对路径；PS5.1 缺 `GetRelativePath` | 含空格/中文目录及支持的 PowerShell 环境失效；具体构建失败需专项复现 |
| U04 | P0 | release 在复制前检查源目录；`-SkipStaging` 仅检查清单存在，源码确认 | 漏文件、旧 staging、版本错配仍可能进入安装包 |
| U05 | P0 | rustup-init 下载默认验证恒真；Zig 只检查 ZIP 可打开；目标载荷只检查存在及长度，源码确认 | 缓存、镜像、错版或非空损坏不能被当前规则充分识别 |
| U06 | P0 | 部分清单路径仅拼接/前缀检查，删除未选组件前缺统一目录边界校验，源码确认 | 异常清单可能越出管理目录；检查也可能误认目录归属 |
| U07 | P0 | staging/sysroot 先删后建；分片直接覆盖公开文件；固定临时目录，源码确认 | 中断破坏上一份可用状态，并发相互覆盖 |
| U08 | P1 | 构建环境保存范围不覆盖全部修改；Cargo 配置按文本删除整个 Windows target section，源码确认 | 目标切换污染、用户合法配置被误修、故障不可恢复 |
| U09 | P1 | sample 有大量 crates 依赖，release 未复制 Cargo registry/git；现有文档已声明第三方依赖自备 | 断网干净安装上的样例和自检闭环不稳定 |
| U10 | P1；发布子集属 P0 | 自包含检查主要跟踪独立探针的 `.lib`；Linux 检查只构建 sample；多处测试依赖源码正则 | 缺少真实 cc-rs、proc-macro、宿主 C、目标运行和安装包回归证据 |
| U11 | P1 | AArch64 wrapper 丢弃硬件勘误修复参数；Windows shim 支持面有限，源码确认 | 已能链接的程序仍可能存在运行行为边界 |
| U12 | P1 | 安装校验先写 manifest，失败仅留 warning；部分 rustc 探测无单命令超时；文档与安装器不一致 | 成功安装与可用状态难区分，故障恢复和现场诊断不足 |
| U13 | P2 | 版本、target、wrapper 模板、原生命令辅助代码分散重复；默认 CI 子进程等待无超时 | 版本维护和排障成本高，门禁可能长时间无结果 |
| U14 | P2 | 发布使用全量复制/重建，包体和缓存缺基线 | 性能优化缺依据，容易以牺牲离线能力换空间 |

## 5. 分项实施方案

### U01：建立契约快照和可执行兼容性基线

**现状证据**：Windows sysroot 的明确契约在 [x64-windows-link-inputs](../openspec/specs/x64-windows-link-inputs/spec.md)；参数和 JSON 分别存在于各脚本。安装器 `GetSelectedComponents` 固定返回三个目标，staging 的 `DefaultComponents` 却仍为 armv7，客户文档还描述可选安装。

**实施任务**：

1. 用 PowerShell AST 提取对外脚本参数，记录类型、默认值和合法值；记录无参数入口及 dot-source 使用方式。
2. 从现有代码生成 JSON 样本和目录样本，给 HEC 已公开的 sysroot/target-libdir 探测增加文件布局回归。
3. 为正常构建、缺少组件、Cargo 失败、wrapper 失败记录退出语义与关键输出，不对时间、绝对临时路径等非稳定信息做逐字断言。
4. 明确三种事实：安装器全量安装；finalize 保留部分组件参数能力；旧 `defaultComponents` 字段值保持。文档分别说明，不能简单把三者“统一”而改变接口。
5. 后续各项必须提供契约差异报告；允许的内部变化单独列出，未解释的差异禁止合入。

**验收**：基线覆盖第 3 节全部入口；旧命令和旧 JSON 读取夹具通过；已有路径未移动；不要求下游修改代码。

### U02：让全新准备流程直接得到完整可构建工具链

**现状证据**：[rust_setup.ps1](../scripts/rust_setup.ps1) 安装 Rust/Zig 并生成 wrappers，但没有调用 `build_win_link_inputs.ps1`；[rust_build_isolation.ps1](../scripts/rust_build_isolation.ps1) 的 `Initialize-WindowsHostLinkInputs` 在四类构建中使用并要求 sysroot 存在。README 的首次安装路径没有补充这一步。

**实施任务**：

1. 保留 setup 原调用方式，在 Rust/Zig/wrappers 就绪后内部调用现有生成器，使首次安装和重复安装都具备 Windows 宿主链接输入。
2. 检查 cargo/rustc/rustup、rust-lld、rust-objcopy、目标 manifest、sysroot 必需文件和 wrapper 的实际存在；不只检查可执行文件版本。
3. 将准备流程分成可重入步骤；正常重复执行只修复缺失或失配的受管资产。保留 `-Force` 清理既有 Cargo 缓存的含义。
4. 对受管 Rust 组件修复仍使用当前 rustup 流程；失败时明确命名未恢复的目标，禁止退回系统 Rust。

**兼容性**：增加的是原有命令本应完成的准备工作，不新增用户操作，不调整 target 或 ABI；修复生成器也沿用现有名称。

**验收**：从没有 tools 二进制的副本运行一次 setup，随后四个旧构建入口可用；无 VS/SDK 环境可构建包含宿主 build.rs 的项目；重复 setup 不破坏已完成状态。联网准备和断网客户安装必须分开验证。

### U03：路径、编码和 PowerShell 双版本兼容

**现状证据**：`Initialize-WindowsHostLinkInputs` 把 `/LIBPATH:<root>` 拼到空格分隔的 rustflags；native wrapper 把 Zig 绝对路径写进 ASCII 文件；`prepare_offline_release.ps1/Get-RelativePath` 直接调用 `System.IO.Path.GetRelativePath`。

Cargo 区分普通空格字符串与参数数组，配置来源也有明确优先级；全局 encoded rustflags 不能简单用来替代每个目标配置，否则可能覆盖裸机链接脚本等设置。实现应依据 [Cargo 配置文档](https://doc.rust-lang.org/cargo/reference/config.html#buildrustflags)，并以固定 Cargo 1.98 的实测结果为准。

**实施任务**：

1. 建立统一的 Windows 原生命令参数编码/调用辅助层，在参数进入进程边界前保留数组语义。
2. 对含路径的目标专属参数，验证临时 TOML 数组配置或私有 linker wrapper 两种实现，选择能保持现有 host/target 优先级的方案；保留外部脚本和环境变量契约。
3. 生成含中文绝对路径的 PowerShell 文件时使用 PS5.1/PS7 都能正确读取的编码；尽量让 wrapper 从自身位置解析安装根，减少嵌入绝对路径。
4. 给相对路径计算提供 .NET Framework 可运行的内部实现，处理跨盘、大小写、尾分隔符和目录边界；不提高 PowerShell 最低要求。
5. 覆盖 CMD 到 PowerShell 到 Zig 的每个转交环节：引号、空字符串、`-out:`、`@response`、空格、中文、`&`、括号；必要时补充长度边界。
6. 激活同一工具链多次时 PATH 不无限重复；从 A 根搬到 B 根之后，各工具实际访问 B 根。已有会话需按现有方式重新激活，不承诺热搬迁正在运行的进程。

**验收**：在 PS5.1 和 PS7 下完成包含空格/中文的安装根、项目根、TEMP 路径矩阵；搬迁后四类构建及 BIN/HEX 生成通过；构建日志和工具解析结果没有旧根泄漏。

### U04：把发布验证移到真正的交付载荷上

**现状证据**：`Invoke-PrepareOfflineRelease` 在复制 staging 之前执行 `Ensure-TargetRustStdPayloads` 和 `Assert-WindowsSelfContainment`，复制后仅写清单；`build.ps1 -SkipStaging` 只检查 `install-layout.json` 存在。

**实施任务**：

1. 保留源目录检查作为快速失败步骤，在 staging 构造完成后额外验证每个清单条目、目标组件和主机工具。
2. 将 staging 的 core 与目标目录在独立临时根组装成安装视图，执行当前 finalize 和旧激活/构建命令；该根必须与源码 tools 根不同。
3. 在隔离验证进程中设置 `RUSTUP_AUTO_INSTALL=0`、Cargo 离线模式，并在测试机层面阻断网络；移走/禁用源码根的工具可见性，证明验证没有借用源码缓存或系统 Rust。
4. 验证四个目标，包含 Windows 主机程序、交叉目标的宿主 build.rs/proc-macro、裸机 BIN/HEX 生成。发布所需最小无网络夹具优先，实际 sample 的离线依赖由 U09 补齐。
5. `-SkipStaging` 继续表示复用既有 staging；仍需只读校验 staging 的产品版本、工具版本、载荷摘要及完整性。不能把它解释为跳过安全性和正确性检查。
6. ISCC 完成后，在发布验证机上实际安装 EXE 并断网执行最小验证；通过后才导出正式分片。校验不通过时保持上一份正式清单。
7. 若 ISCC 返回成功但预期 EXE 不存在，发布失败；不能仅输出警告后结束。

**兼容性**：所有发布命令和产物命名保持；加强发布条件，客户无需新增步骤。安装后尽力校验的旧退出语义不承担正式发布门禁职责。

**验收**：故意遗漏复制文件、使用旧 staging、修改版本、移除 rust-objcopy、破坏任一目标 rlib、拒绝网络或隐藏源码工具后，发布正确拒绝或正确通过；必须有最终 EXE 的安装验证记录。

### U05：下载可信度与完整性验证贯穿组件生命周期

**现状证据**：`Ensure-Download` 已有临时文件与成功后移动，这是应保留的基础；但 rustup-init 使用默认恒真验证，Zig 只调用 `Test-ZipArchive`。目标检查没有逐文件摘要，`rustc -vV` 输出也未与每份组件的来源绑定。`PROVENANCE.json` 已记录 sysroot SHA-256，但当前 Windows 自检主要检查符号而非重算全部文件摘要。

**实施任务**：

1. 建立受版本控制的内部依赖锁定数据：现用 Rust release/commit、Zig 版本、受信任 bootstrap 版本/摘要、对应来源及工具资产摘要。值由发布维护者在可信来源下核实，不在本计划臆造。
2. 对所有下载和命中缓存执行摘要验证。直接 URL、镜像、代理仍遵循当前优先级，来源改变不能绕过内容校验。
3. 明确 rustup-init 当前 URL 是可变分发入口，不能用一次网络下载的结果自证可信；通过维护的可信版本/摘要集合和内部缓存保持可重复性。出现合法上游更新时更新内部锁定数据，不要求客户增加新参数。
4. 由同一次受管安装建立组件文件摘要、rustc commit 和 target 清单的绑定；不能用 rlib 文件名中的 hash 直接当作 rustc commit。
5. 保留现有“manifest + 锚点 + 非空”快速检查，在发布/安装载荷检查中增加完整摘要复核和最小真实编译。普通激活不强制反复哈希整个数 GB 工具链。
6. sysroot 发布验证核对全部 13 个 `.lib`、PROVENANCE 与必需符号，不把当前 7 文件就绪检查当成完整审计；保留 HEC 既有最小路径探测方式。
7. 新增完整性索引作为内部受管文件使用，既有 JSON schema 不变。旧包缺少内部索引时走已有兼容校验；新发布包必须带有内部索引。

**验收**：镜像返回 HTML、合法 ZIP 但内容错版、非空损坏 rlib、同名错误库、缓存遭替换，都在使用前或正式发布前被识别；验证成功记录可定位到具体编译器与组件来源。

### U06：统一受管路径边界，避免清单驱动的越界操作

**现状证据**：`Test-RustTargetPayload` 检查字符串以 `lib/rustlib/<triple>/` 开头，随后直接拼接；`Remove-UnselectedComponentFiles` 信任 JSON 相对路径；`Test-InsideToolkit` 对完整路径直接做根字符串 `StartsWith`，未加入分隔符边界。

**实施任务**：

1. 清单相对路径统一拒绝绝对路径、盘符、UNC、`..`、空路径、根路径、备用数据流形式及不允许的重解析点。
2. 拼接后规范化绝对路径，按不区分大小写的“根目录本身或根目录加分隔符”判断归属；不能把 `C:\kit-other` 当作 `C:\kit` 内部。
3. 对删除、移动和安装修复增加更窄的受管文件白名单；先完整验证清单，再开始任何修改，避免执行一半才发现恶意/损坏路径。
4. 校验 `SelectedComponents` 只能引用布局中已定义目标，保留当前空值和正常子集语义；未知组件在修改前给出明确错误。
5. 发布、sysroot 生成和测试清理使用同一内部边界检查规则，尤其是用户可传入的 OutputRoot/ToolkitRoot 和 TEMP 路径。

**验收**：以隔离测试目录中的根外哨兵文件验证 `..`、同前缀兄弟目录、UNC、junction 等用例；所有非法清单在首个写入/删除前失败，哨兵文件保持原哈希。不能在开发者正在使用的 tools 上注入破坏测试。

### U07：安装准备、staging、sysroot 与分片发布的事务和并发隔离

**现状证据**：staging 刷新先删除旧目录，sysroot `-Force` 先删除 lib；native C wrapper 和 Windows 自包含探针使用固定 TEMP 子目录；负向测试会临时移走真实 sysroot；分片直接写目标文件，最后直接覆盖公开 JSON。

**实施任务**：

1. staging/sysroot 在同卷临时目录完成生成与校验；获取写锁后切换到正式路径，保留可恢复的上一状态。Windows 文件占用导致无法切换时，保持旧状态，不继续部分覆盖。
2. Rust 目标修复不能简单宣称“目录 rename 即原子”：应按 rustup 的 homes、components、manifests 一并制定恢复流程。优先在隔离准备副本中修复并验证，避免边构建边删除当前组件。
3. 写锁按规范化工具链根和操作对象区分；setup、生成器、staging 等写操作互斥；构建不能消费切换到一半的载荷。锁记录进程身份/开始时间，正确处理异常退出，不能仅凭 PID 判断过期。
4. native wrapper 使用每次调用的独立临时目录或带锁的稳定私有目录，防止两个工具链根互相覆盖 Zig 绝对路径；成功、失败、超时均清理。
5. Windows 负向测试改在隔离副本运行，不搬走开发者或同一 CI 中其他构建正在使用的正式 sysroot。
6. 分片在私有临时目录生成，验证每片长度/摘要、总长度、重新拼接摘要；完成后移动到既有文件名，**最后原子替换公开 manifest**。
7. 不允许在仍被公开 manifest 引用时原位覆盖同版本不同内容。相同版本同内容可幂等复用；同版本内容冲突拒绝发布。并发发布加锁；保留旧版本文件供旧清单完成下载，清理由独立保留策略控制。
8. 明确事务边界：EXE 导出成功不等于分片已正式发布；只有完整校验并完成 manifest 切换才记录发布成功。

**验收**：复制、压缩、分片中途注入失败或进程终止后，旧工具链/旧公开清单仍可用；两个根并行构建互不影响；同根两个发布者不会写出混合版本；不会产生指向缺片的新清单。

### U08：环境与 Cargo 配置修复的最小影响范围

**现状证据**：各 build 脚本在快照前覆盖 Rust 镜像变量；native build 修改 PATH、homes、toolchain、Zig 缓存，现有隔离名单主要覆盖目标构建和 VS 变量。配置修复器按行删除任意 `target.x86_64-pc-windows-*` section，可能删除用户设置。当前未见对 `RUSTC`、`RUSTC_WRAPPER`、`CARGO_BUILD_RUSTC` 等选择器的完整策略。

**实施任务**：

1. 把环境划分为激活所需持久状态和单次构建的临时状态，先对当前调用习惯做基线；保留显式 `rust_env.ps1` 激活后的公开变量。
2. 对新增/已有的临时状态统一 save/restore，尽量在构建子进程中施加；成功、失败及取消都验证恢复。native 构建是否保留激活效果按 U01 基线处理，不能直接一律恢复而改变旧调用语义。
3. 对 Cargo、rustc、linker 的实际解析路径增加验证，受管选择使用绝对路径；识别外部 RUSTC 和 wrapper 注入。合法用户 compiler wrapper 是否仍允许，必须先保持现行合法用法，不做未经验证的全局清空。
4. Cargo 配置修复限定为可识别的历史工具链残留键，不删除整个用户 Windows target 表；保留 runner、自定义 cfg、source replacement、registry、alias 及与工具链无关的 rustflags。
5. 修改配置前留可恢复副本，采用临时文件替换；无法可靠解析时停止自动改写并明确诊断。优先使用临时覆盖实现相同的链接效果，但须测试 Cargo 的数组合并和优先级。
6. 对 toolkit 根、项目根、ambient Cargo home 分别确定修复授权边界；保留安装收尾已经使用的 `SkipAmbientCargoHome` 保护。

**兼容性**：目标、构建 profile、旧入口和输出路径不变；不借此开放新的编译配置 API。既有冲突修复应继续有效，非冲突用户配置不再受损。

**验收**：一会话内 armv7 → Windows → thumbv7em → aarch64 连续构建；故意失败后环境符合基线；带 workspace、旧 config 文件、cfg target 表、中文注释、source replacement 的项目保持预期配置和产物。

### U09：建立可在干净客户环境执行的离线样例与自检

**现状证据**：[sample/Cargo.toml](../sample/Cargo.toml) 包含 tokio、reqwest、clap、serde 等依赖；core 复制 Cargo bin，但不复制 registry/git，安装器仅创建空缓存目录。客户文档正确说明工具链离线不等于任意依赖离线；问题在于当前 bundled sample 和 Windows 自检自身也依赖这些外部包。

**实施任务**：

1. 保持现有 sample 的功能和调用方式，按已提交 Cargo.lock 在发布准备机收集其精确依赖和目标相关依赖，不复制开发者整个 Cargo home。
2. 在发布私有副本评估两种交付实现：最小受管 Cargo 缓存，或仅作用于样例目录的 vendor/source replacement。选定后验证旧构建命令不变，不能污染客户其他项目的 source 配置。
3. 去除 credentials、私有 token、个人 registry 配置、绝对用户路径等非必需内容；为所交付依赖保留 license 文本和清单。
4. 自检保留无依赖最小夹具作为工具链故障定位基础；完整 sample 作为真实依赖兼容用例，不能只用 hello-world 替换它掩盖问题。
5. 离线验证须同时保证 Rust 组件、Cargo 包和 C build script 使用的资产在包内；Cargo offline 不能阻止任意 build.rs 自己联网，因此测试机仍需实际断网。
6. 不对客户普通构建强制 `--offline` 或 `--locked`；这些限制只施加在发布验证进程及已锁定的自检夹具中。

**验收**：全新用户、空系统 Cargo cache、无系统 Rust、网络禁用后，随包样例和自检成功；缺依赖时报告依赖准备问题，而非误报工具链损坏。外部参考：[Cargo vendor](https://doc.rust-lang.org/cargo/commands/cargo-vendor.html) 描述了依赖收集与 locked/offline 的边界。

### U10：把自包含和多目标验证从声明变成证据

**现状证据**：Windows 自检已有有价值的运行时夹具，但其 C build.rs 直接编译对象、刻意绕过 archiver，并未覆盖真实 cc-rs；库来源来自额外的 rustc 探针，只匹配 `.lib`；Linux 检查调用 sample 构建，不运行 Linux 产物。

**实施任务**：

1. 保留现有 runtime 夹具，增加锁定且离线可用的 cc-rs 夹具，实际经过 CC、AR、RANLIB；增加 proc-macro 和“build-dependency 自己包含宿主 C 代码”的交叉编译夹具。
2. 区分 target C 编译器和 host C 编译器。在 Linux 构建中只设置目标 CC 并不能证明宿主 C build-dependency 不会寻找 MSVC；用无 VS 环境验证后补齐内部 wiring。
3. 跟踪真实 Cargo 构建执行的工具路径和链接输入，不只检查独立探针。对 `.lib`、`.a`、rlib、响应文件及库搜索路径形成可审计记录；工具/系统运行时允许项与项目源码、target 输出应分类，不能要求所有输入都在 toolkit 根内。
4. Windows 产物检查 PE 架构、依赖 DLL 和运行行为；Linux 产物检查 ELF 架构、hard-float/ABI、动态解释器和依赖项，按当前产物基线判定是否维持原链接模式。
5. Linux 在独立验证机或 QEMU/实际板卡上执行最小文件、线程、时间、网络功能测试；模拟器只作为开发/发布验证基础设施，不成为客户工具链依赖。
6. 裸机验证 vector table、初始 SP、Reset 地址、段位置、BIN/HEX 加载地址及容量；实板验证单独记录，不能把链接成功等同于固件已在 HEM6801E 运行。
7. 默认 CI 保持轻量，文件检查和 mock 行为测试不下载工具；Full 保持原入口，扩大真实构建覆盖；正式发布另外强制完成不可跳过的安装和断网验证。
8. 将仅检查源码中“出现某字符串”的测试逐步替换为假可执行文件采集 argv/env、故障注入、文件前后快照。保留必要的公开路径静态断言。

**验收**：人为注入系统 rustc、宿主 SDK 路径、错误 archiver、外部 C 工具和错误 target 时，测试能够解释性失败；正常四目标样例通过；验证报告明确列出尚未执行的 OS/硬件组合。

### U11：现有 ABI 和硬件兼容性的专项验证

**现状证据**：[AArch64 wrapper](../tools/wrappers/aarch64-linux-musl-gcc.ps1) 明确过滤 `--fix-cortex-a53-*`；Windows 生成器提供手写 startup、TLS、栈探测和窄字符格式化函数；宽字符族尚未提供。

**实施任务**：

1. 对 Cortex-A53 参数过滤建立最小复现、受影响 CPU 清单和产物检查，确认当前目标客户是否受影响。wrapper 的注释已承认绕过修复，不应继续把这一点当纯粹的参数兼容问题。
2. 在不换 Zig 版本、目标 triple、CPU 默认值和外部 wrapper 名称的条件下，评估能保留勘误修复的内部链接调用路径；若无法证明兼容，则本轮只交付风险范围、回归和验证结论，将工具版本/CPU 策略调整移出本轮。
3. Windows 增加命令行 Unicode/引号/通配符、环境变量、TLS 析构、atexit、panic/unwind、较大栈帧、格式化边界等用例。对自定义 startup 尤其要验证初始化/退出语义，而不只确认符号存在。
4. 用真实依赖确认是否需要补宽字符 printf/scanf 或额外 Win32 import library；只增加由实际需求和行为测试支持的实现，沿用现有 lib 目录和 PROVENANCE 结构。
5. 明确 C ABI 与 C++ ABI 的支持边界；不宣称 mingw C++ 异常/对象可以任意与 MSVC 对象混用。

**验收**：现有 Windows fixture 继续通过，新增 runtime 用例给出结果；AArch64 workaround 有可追溯的适用范围和测试；没有偷偷切换 ABI、CRT 策略或硬件最低要求。

### U12：安装可诊断性、修复与文档一致性

**现状证据**：finalize 先生成 install-manifest，再在 `-Validate` 中尝试健康检查，异常被转成 `install-validation-warning.txt`；`Get-RustTargetPayloadStatus` 内部 rustc 探测没有走已有单命令 timeout；Inno 使用 `[Run]` 同步等待，没有显式读取业务校验结果；PATH 在安装步骤中另行处理。

2. 内部区分文件部署、配置写入、载荷检查、编译检查状态；沿用既有清单 schema，详细结果写内部日志。只有完成对应检查才在报告中标记通过，部署 manifest 不作为健康证明。
3. 全部外部验证命令使用统一限时执行，包括 target-libdir 探测；保留总 watchdog，避免累计等待超过总期限。正常完成和异常终止都能留下已完成阶段的信息。
4. 对 Inno 与 finalize 的结果处理做专项验证。若增加结果读取，可参考 [Inno Exec 文档](https://jrsoftware.org/ishelp/topic_isxfunc_exec.htm)；本轮只接入内部日志与发布验收，不擅自改变安装器旧退出协议或增加客户确认流程。
5. 校验失败后保留已有 warning 文件和格式；后续验证成功时清理过期 warning，避免修复后继续误报。日志不得泄漏代理凭证或下载 URL 中的 token。
6. 覆盖重复安装、同版本修复、升级中断、部分目标的 finalize 调用；旧版本残留只能按受管清单清理，不能清空用户 registry/cache/project。
7. 验证 perUser/perMachine、D 盘存在/缺失、默认路径不可写、目标路径被占用的行为；保留既定默认安装路径和权限策略，不通过改为管理员安装掩盖问题。
8. 修正文档：安装器当前全量安装三个目标；区分脚本激活和安装器持久 PATH 修改；区分宿主支持 OS 与产物支持 OS；补上真实的离线依赖边界；更正 sample_embedded 的 objcopy 注释。

**验收**：安装不会因子进程挂住无限等待；失败阶段可定位且旧输出契约保持；已修复安装不留失效警告；文档描述与现行实现一致。

### U13：内部单一配置来源、行为测试与门禁限时

**实施任务**：

1. 把 Rust/Zig 固定版本、host triple、目标清单、所需工具、wrapper 定义提取成内部数据；保留原脚本作为薄入口，不增加用户配置步骤。
2. 复用现有 target payload 定义，减少 release/finalize/环境脚本中的重复 triple；生成结果仍是原来的文件名和 JSON 格式。
3. wrapper 从一份模板生成，并验证已跟踪 wrapper 与 setup 生成结果一致；不要维护两套会漂移的参数过滤逻辑。
4. 统一原生命令调用、编码、超时、退出码检查和作用域环境管理，避免每个脚本重写一次。
5. CI 外部检查增加合理的单项和总超时，并终止自身启动的进程树，输出具体失败项；保留默认 SKIP 和 Full 含义。正式发布验证不能因缺测试基础设施而以 SKIP 当通过。
6. 在固定验证环境记录本次默认门禁最慢套件约 39.9 秒的基线；README 的“约 12 秒”只是旧描述，性能承诺应按重新测量结果修订。
7. 每次内部重构单独提交并执行 U01 契约比较；避免同时修改模板、版本、格式和行为，导致无法定位兼容性差异。

**验收**：数据源变化不要求修改多个脚本中的同一个常量；生成文件无漂移；PS5.1/PS7 的错误和参数行为一致；假子进程挂起能在规定时间内结束且不影响其他任务。

### U14：可重复发布、性能和分发成本优化

**实施任务**：

1. 记录每次发布的文件数、各组件大小、EXE/分片大小、下载/解压/校验/构建/压缩耗时、冷/热构建耗时；报告留在内部发布记录，不添加对外必填字段。
2. 源文件顺序固定；对 sysroot 库文件验证相同输入下摘要稳定；安装包本身因生成时间、压缩工具版本或签名时间可能不逐字节一致，应分别定义“载荷一致”和“EXE 一致”。不能把两者混为一个承诺。
3. sysroot 增量复用的 key 至少包含 Zig 版本、生成器内容、来源资产和配置摘要，不能仅凭 `zig version` 跳过重建。
4. staging 可按内容摘要复用未变文件，但与工作工具链隔离；慎用硬链接，避免后续写入修改源载荷。
5. 只精简可证明不参与任何现有功能的文件；不删除 mingw 头文件/definition、rust-objcopy、目标 std/core、wrapper、离线自检依赖或许可文本。
6. 为实际交付的 Rust、Zig、mingw、shim 和样例依赖形成内部组件/许可清单，保存对应许可证。exe 签名若采用，应在发布侧完成，不引入客户联网或新的必填验证协议。

**验收**：同输入 sysroot 内容稳定；性能指标与 U04/U10 通过结果一起比较；建议热构建耗时相对同机基线回退不超过 10%，超出必须有功能/完整性成本说明。具体包体和时延目标在基线测量后确定，当前不承诺虚构的节省百分比。

## 8. 回退策略与明确排除项

### 8.1 回退策略

- 代码回退按小提交进行，不回滚客户项目、不执行全局 Rust 卸载。
- 构建/配置修复先保存原内容；恢复只覆盖本次操作管理的文件，校验恢复前后的摘要。
- staging/sysroot 新版本验证通过才切换，失败保留上一份可用状态；锁不跨根误伤其他安装。
- 发布 manifest 只在新分片完整后替换；保留上一份清单和其引用的完整分片，回退只切回已验证清单。
- 原则上禁止同一产品版本重新发布不同内容；必要重发使用新的现有格式版本号，避免旧客户端缓存混用。
- 若某项实现需要更改默认参数、既有 JSON、安装目标选择、ABI、公开路径或有效调用的退出语义，停止该实现并从本轮剥离；其他兼容改进继续推进。

### 8.2 不纳入本轮

- 新增操作系统宿主、RISC-V/WASM 等目标或目标管理 GUI。
- 切换 `x86_64-pc-windows-gnu`、引入 xwin/客户现场下载微软 SDK，或改变默认 CRT 策略。
- 升级 Rust/Zig、改变固定 toolchain 目录、最低 CPU 要求或用户项目的默认编译 profile。
- 新增必需 CLI 参数、必需环境变量、必需外部服务或强制在线许可证步骤。
- 将“便携”重新定义为不保留现有安装器 PATH 行为；改动用户/机器安装作用域或默认安装位置。
- 修改 HEC Target 包来绕过工具链载荷缺失；标准库和链接器仍由本工具链负责。
- 对任意第三方 crate 承诺全部离线、全部 C/C++ ABI 兼容，或仅凭本机测试扩大 OS/硬件承诺。

本计划的完成标准是：现有用户和 HEC 集成方继续使用原命令、原路径与原格式，同时发布物能证明完整、可搬迁、断网可验收，并在失败和并发情况下保住上一份可用状态。
